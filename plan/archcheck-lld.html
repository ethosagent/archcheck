archcheck — Low-Level Design

The design reviewed against its own failure modes, every open question decided, and specified concretely enough to start writing code.

archcheck v0 · 20 September 2026

1 · Critical review — what was wrong

Twelve problems found in the design as written. Nine needed a fix, three are accepted limits now stated honestly instead of glossed over.

1 · Editor feedback would have lost the remedy

Was: emit a lint config, and the editor shows the underlying linter's own message — a rule name with no statement and no remedy. The best feedback moment, wasted.

Now: the emitter writes the statement and remedy summary into the lint message text itself. The editor squiggle already reads "domain may not import services — invert the call". archcheck adds the structured form on top; it is not the only way to get a useful message.

2 · One rule can need several configs

Was: ContractType.emit(rule) → config. But encapsulation needs both a package exports map and a graph rule. Layers may need a lint rule for the dynamic-import ban alongside the graph rule.

Now: emit(rule) → Fragment[], each fragment targeting one sink. The merger groups fragments by target and writes one file per sink.

3 · It would have re-run the whole check suite

Was: ambiguous whether archcheck runs the type checker, linter and graph tool — which would duplicate every other gate and double CI time.

Now: every probe can either run a tool or ingest its existing report. CI runs each tool once, writes its JSON, and archcheck normalises. Locally, running them directly is the convenience path.

4 · No baseline — so no rule could ever be added to existing code

Was: a rule is on or off. On an existing codebase, turning a rule on means fixing every violation first, which means nobody turns it on.

Now: a ratchet. baseline.json records known violations by stable identity hash, never line number, so moving code does not resurrect a finding. The run fails on new violations only, and also fails if a baselined finding is gone but still listed — so the file shrinks as debt is paid and cannot silently over-suppress.

5 · No way to grant a genuine exception

Was: "exemptions with an expiry" asserted, never designed. In practice people then use inline comments, which spread and are never reviewed.

Now: exceptions live in the manifest only — never inline — each with an owner and an expiry date. An expired exception fails the run. Inline suppression comments are themselves a lint error.

6 · Rule ids could be renamed, breaking history

Was: "stable ids" claimed, with nothing enforcing it. A rename silently orphans every baseline entry and every historical annotation.

Now: ids are immutable once committed. Renaming means a new id plus replaces: 'old-id', and a check fails if a committed id disappears without one.

7 · The model probe had no failure path

Was: judgement rules assume a model is reachable. In CI without credentials, in a sandbox, or offline, the run would break.

Now: the judgement probe skips cleanly with no credentials and says so in the summary, exactly like a live test. It also carries a concurrency cap and a per-run spend ceiling, and refuses rather than overspending.

8 · "Incremental" was overstated

Was: "only changed files and their dependents are re-checked" — but computing dependents needs the whole graph anyway.

Now: stated honestly. The graph is always built; caching saves the parse, and diff-scoping saves rule evaluation and every model call. That is where the real cost is, so the benefit stands — the claim was just wrong about why.

9 · Doc generation would have bloated the manifest

Was: generate the whole patterns document from the manifest, which means every paragraph of prose lives in a config file.

Now: the manifest holds only the short statement and remedy, and generates the rule table and the coverage counts. Long-form prose stays hand-written in the patterns document. The generated region is marked, and hand-editing it fails a check.

10 · No standard output format for CI

Was: a bespoke JSON shape, which no CI platform understands.

Now: SARIF is the CI format — consumed natively by code scanning and editor viewers, and diffable across runs. Our richer Diagnostic remains the agent format, carried in SARIF's properties bag so nothing is lost.

Three limits, accepted

One config per repository

No per-package manifests. Simpler, and the architecture is repository-wide by definition. Revisit only if a second product shares the repo.

Static only

Nothing observes runtime. A rule about what happens under load is out of scope and always will be.

Model verdicts stay advisory

Promotable per rule, but the default never changes. A non-deterministic blocking gate is how a check suite loses trust.

Verdict after review. The three-seam shape held — every problem above was a detail inside a seam, not a missing seam. That is the signal worth having before implementation starts.

2 · Types

Five types. Everything else is a function between them.

// ─── what the consumer writes
type Rule = {
  id: string;                      // immutable once committed
  kind: ContractKind;              // closed set — see §4
  statement: string;               // one sentence, goes into the lint message
  severity: 'error' | 'warn' | 'advisory' | 'off';
  confidence: 'deterministic' | 'proxy' | 'model';
  params: Record<string, unknown>; // kind-specific, validated by the kind
  remedy: { summary: string; allowed?: string[]; autofix?: boolean; docs?: string };
  replaces?: string;               // set when an id is superseded
  owner?: string; expires?: string;// required on an exception
};

// ─── what a probe returns, before enrichment
type RawFinding = {
  ruleId: string;
  file: string; line?: number; col?: number; endLine?: number;
  evidence: Record<string, unknown>;  // { from, to } for a graph edge, etc.
  identity: string;                   // stable hash — survives line moves
};

// ─── what everything downstream consumes
type Diagnostic = RawFinding & {
  schemaVersion: 1;
  statement: string;
  severity: Rule['severity'];
  confidence: Rule['confidence'];
  remedy: Rule['remedy'];
  detectedBy: string;
  baselined: boolean;
};

// ─── emitted config, grouped by sink
type Fragment = { target: 'graph' | 'lint' | 'boundaries' | 'test' | 'exports'; content: unknown };

type RunResult = {
  ok: boolean;
  diagnostics: Diagnostic[];
  skipped: { probe: string; reason: string }[];
  coverage: { total: number; deterministic: number; proxy: number; model: number };
};
The identity hash is the load-bearing field. Baselining, deduplication and "did my fix work" all key off it. Compute it from ruleId plus the semantic evidence — the import edge, the symbol name — never the line number.

3 · The three seams

interface ContractType {
  kind: ContractKind;
  validate(rule: Rule): Result<void, string[]>;   // params well-formed?
  emit(rule: Rule, ctx: EmitCtx): Fragment[];      // one rule → many sinks
  explain(f: RawFinding, rule: Rule): string;      // finding → human sentence
}

interface Probe {
  name: string;
  handles: ContractKind[];
  // run it, or ingest a report another gate already produced
  run(ctx: RunCtx): Promise<RawFinding[] | Skip>;
  ingest?(report: unknown): RawFinding[];
}

interface Reporter {
  name: string;
  report(r: RunResult, ctx: ReportCtx): Promise<string | void>;
}
new kind of ruleImplement ContractType. Rare — the closed set in §4 covers everything we have.
new checkerImplement Probe. A security scanner, a bundle budget, a schema differ.
new audienceImplement Reporter. Nothing upstream changes.
new ruleNothing. One entry in the manifest. This is the common case and must stay the common case.

Adding a ninth kind is a design decision, not a task. Every kind costs a validator, an emitter, an explainer and a test fixture. If a new rule can be expressed as an instance of an existing kind, it must be.

8 · Build order

v0.1 · walking skeletonTypes, registry, layers kind, graph probe, terminal + json reporters, emit and the run. One rule end to end, with its fixture violation. Proves the whole pipe before anything is broad.
v0.2 · the structural setencapsulation, banned-syntax, naming · lint probe · the statement-in-the-message trick. Covers the load-bearing rules.
v0.3 · adoptionBaseline ratchet, exceptions with expiry, exit codes, emit --check. Without this it cannot be turned on anywhere that already has code.
v0.4 · the rest of the structurerequired-file, declared-field, structure probe, SARIF reporter, coverage accounting.
v0.5 · judgementThe model probe, caching, budget cap, clean skip. Advisory only. Last, deliberately — everything before it must work without a model.
v0.1 is one rule, not one feature. Pick domain-no-service-import, carry it from manifest entry through emitted config, violation, normalisation and both reporters, with a fixture that must fail. Everything after that is breadth.

9 · The three open questions, decided

9.1 · Where it lives — in-tree and published

These were never in tension. It lives at packages/archcheck/ in the main repository and publishes to npm from there. Monorepo publishing is ordinary, and it buys both properties at once.

why in-treeThrough v0.1–v0.2 the seams will move. Every seam change across a package boundary is a version bump, a release and a bump-back in the consumer — a day of friction per change, at exactly the moment changes are most frequent.
why still publishedNothing about living in the repo stops npm publish from that directory. The package name is reserved from day one, and adopting it elsewhere never requires a migration.
when to extractOnly if a second repository depends on it and the seams have survived roughly ten real rules unchanged. Until both are true, extracting costs more than it returns.
the boundary is still realarchcheck imports nothing from the engine — enforced by archcheck. If it cannot hold its own dependency rule, it has no business holding anyone else's.

9.2 · Fixtures — two suites, different jobs

The tension was real: package-owned fixtures cannot use the consumer's layout, and consumer-owned fixtures cannot self-test the package. The answer is that these are two different questions and each needs its own suite.

In the package — does the mechanism work?

Tiny synthetic repositories, one per contract kind. Generic, never World-Engine-shaped. Proves that layers emits correctly, detects correctly and normalises correctly. Ships with archcheck and runs on every change to it.

In the consumer — does this rule match?

One deliberate violation per rule instance, in the real layout. Proves that the rule as configured here actually catches something. A rule whose pattern matches nothing passes every build and looks exactly like compliance.

And the consumer's obligation is itself a rule. Every rule at severity: error must have a fixture that it catches — expressed as a required-file instance, checked by archcheck, on itself. The "test the checker" step stops being discipline and becomes a gate.
{ id: 'every-error-rule-has-a-fixture',
  kind: 'required-file',
  params: { forEach: 'rule[severity=error]', expect: 'fixtures/{id}.violation.ts' },
  severity: 'error',
  remedy: { summary: 'add a file that deliberately breaks this rule, and assert it is caught' } }

9.3 · The judgement probe — provider, credential, cost

The last undecided piece, and the one with the most ways to go wrong. Four decisions.

provider is a seamAn LlmProvider interface with one method, so the probe is never bound to a vendor. Ships with one implementation; a second is a day's work if it is ever needed.
credentials from the environment, never configRead from the environment at run time. No key, no failure — the probe skips and says so. Locally that is the developer's own key; in CI a repository secret. A key never appears in a file archcheck reads.
structured output, not proseThe judge returns a strict schema — verdict, cited span, confidence — so parsing never guesses. A verdict that fails schema validation is discarded rather than salvaged.
budget before the first callA per-run ceiling in dollars and calls, checked before each request. Over the ceiling the probe stops and reports how many rules went unjudged. It never silently spends more.

Two decisions that make it affordable

// 1 · rules are the CACHED PREFIX, the file is the volatile suffix
//    every judgement rule's statement and examples are identical across every file,
//    so they cache once and are re-read at a fraction of the price.

  [ system: judge instructions          ]  ← stable
  [ all judgement rules + examples      ]  ← stable · cache breakpoint here
  [ the one file under review           ]  ← volatile

// 2 · batch by FILE, not by rule
//    judging 15 rules against one file is one call, not fifteen.
//    15 rules x 40 changed files = 40 calls, not 600.
// config — the whole surface
judgement: {
  model:   'claude-opus-5',      // default. 'claude-sonnet-5' is the usual cost trade
  budget:  { maxUsd: 0.50, maxCalls: 60 },   // per run
  scope:   'changed',            // 'changed' | 'all' — never 'all' in a hook
  concurrency: 4,
}
On model choice. Opus 5 is the default because a judge that produces false positives is worse than no judge — people stop reading the advisory stream and the tier dies. Sonnet 5 is the obvious cost trade once the rules are calibrated and their hit rate is known, and it is one config line. Start accurate, get cheaper with evidence.
Files under review are quoted data, never instruction. A source file containing text that reads like a directive is a string being judged, not a command being followed. Stated here because it is the one security property of this probe, and it is easy to lose when someone later "simplifies" the prompt assembly.

Nothing is open

Ready to implement. Every decision this design depends on is made. What remains is v0.1: one rule, carried end to end, with a fixture that must fail.
