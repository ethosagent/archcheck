AI-first architecture conformance

Architecture Checks

Most of this code will be written by a model. Rules are declared once, checked at six moments, and returned as typed diagnostics a model can act on — the same way, every time. The author is non-deterministic; the check is not.

World Engine v6 · 91 rules · 20 September 2026

1 · One file defines everything

No rule is written twice. The manifest is the only place a rule exists; every config, every check and this documentation are emitted from it.

manifest → four outputs

2 · When each rule fires

The same rule set is checked repeatedly, earlier each time it can be. A rule caught at the keystroke costs nothing; the identical rule caught in CI costs a context switch.

91 rules waiting
Read the colours. Green ticks are rules a machine decided. Amber are proxies — the check passed, but the rule is broader than the check. Grey are the ones no check can decide, waiting on a reader.

3 · Six layers, each blind to something

No single mechanism sees everything. The layers overlap on purpose: what one cannot see, the next one can.

7 · What it cannot catch

No import, no edge

A value on the global object, a computed import, a process boundary. The graph sees none of it. Closed by banning the constructs, not by checking harder.

The rule nobody wrote

Default-deny is the answer: a layer with no declaration denies everything, so an undeclared folder fails on its first commit rather than being silently legal.

A checker matching nothing

Reports green forever and reads as compliance. Only the fixture violations tell the difference.

The manifest being wrong

Every check proves the code matches the declared architecture. None of them proves the declared architecture is the one you wanted. That gap does not close.

8 · What the field already worked out

Eight tools in four ecosystems were read before any of this was designed. None of them solves our problem, but between them they have already settled eight questions. Taking these rather than rediscovering them is most of why this can be small.

1 · Rules are typed, never freeform

A rule is an instance of a named contract type — layers, forbidden, independence, naming, required-file, declared-field. Adding a rule is data. The moment a config accepts arbitrary predicates it has become a programming language with no debugger.

2 · Confidence is part of the rule

Some checks decide; some approximate. Recording which is which stops a heuristic from being treated as a proof, and lets a consumer know when to stop trying.

3 · Always leave an escape to code

Anything config cannot express becomes an ordinary test with a custom predicate. Every mature tool has this hatch; the ones that do not end up growing a half-language instead.

4 · A module's public surface is first-class

Not a convention about barrels but a declared property of the module, so the deep-import ban is generated rather than remembered.

5 · Layers are matched by collectors

By path, by name, by implemented interface — not only by folder glob. "Anything implementing this port" is a layer that a glob cannot describe.

6 · File-level, never project-level

Granularity coarser than a file misses every violation inside a project, which is where most of them are. A deliberate non-adoption of the most popular approach.

7 · A diagnostic can carry its fix

For the minority that are mechanical. Being honest about which those are matters more than the feature — a syntactic fix to an architectural violation satisfies the check and breaks the design.

8 · Emit into checkers, do not build one

Graph analysis, AST matching and cycle detection are solved. Writing a fifth implementation is how a small tool becomes a large one.

The one thing none of them does. Every tool reports to a person. None generates the document that describes its own rules, and none tracks which rules have no check at all. That gap is the product.

9 · AI-first: the point of the whole thing

Every tool in Part 8 was built for a human reading a terminal. This one is built for a model writing code. That single difference decides the design: the check is off-the-shelf, and the diagnostic is the product.

Most of the code in this repository will be written by a model. A model does not read the patterns document before each edit, does not carry a convention across a context boundary, and does not notice that it has drifted. It writes something plausible. Plausible is exactly what architectural drift looks like.

The author is non-deterministic. The check has to be deterministic. That is the whole thesis. We cannot make a model reliably remember ninety-one rules, and we do not need to — we need the rule delivered at the moment it is broken, in a form the model can act on, identically every time.

Rules are not prompts

A convention in a document is advice a model may or may not apply. The same convention as a typed diagnostic is a fact it cannot argue with. Move rules out of the prompt and into the check.

Same violation, same message

Determinism is what makes a correction loop terminate. If the feedback varies, the model negotiates with it; if it is identical every run, the model fixes it and moves on.

The loop closes without us

Write, check, receive typed failures, fix, re-check, compare ids. No human in that loop — which is the only way consistency survives the volume.

Consistency becomes measurable

Not "we have conventions" but "sixty-five rules are machine-decided and the build is green". A claim about the architecture that is actually true.

Working name: archcheck — an AI-first architecture conformance engine. Rename it freely; the positioning is what matters. It is not a linter. It is the feedback channel between the architecture and whatever is writing the code.

Why raw tool output fails a model

six dialects in, one schema out

Six formats

A type error, a lint result, a graph violation, a failed assertion and a script's exit code are five unrelated shapes. An agent has to parse all of them and still cannot tell which were architectural.

A name, not a rule

"no-restricted-imports" says what fired, never what the architecture requires. The agent has the symptom and none of the intent.

No remedy

Nothing says what a correct version would look like. The agent guesses, and a plausible guess that satisfies the linter can still be architecturally wrong.

No authority signal

A proxy rule and a decisive one fail identically, so an agent will thrash trying to fully satisfy a check that was only ever an approximation.

The diagnostic is the product

One schema, emitted by every layer. This is the only interface that matters — everything upstream exists to produce it.

{
  "ruleId":     "domain-no-service-import",      // stable, survives renames
  "statement":  "domain may not import services",
  "severity":   "error",
  "tier":       "generated",                     // generated | registered | recorded
  "confidence": "deterministic",                 // deterministic | proxy | model

  "location": { "file": "modules/ledger/domain/supersede.ts", "line": 4, "col": 1 },

  "evidence": {                                  // what actually happened
    "from": "modules/ledger/domain/supersede.ts",
    "to":   "modules/ledger/services/write.ts",
    "via":  ["direct import"]
  },

  "remedy": {                                    // the part an agent uses
    "summary":  "invert the call: the service calls the domain, never the reverse",
    "allowed":  ["contracts", "modules/ledger/rules"],
    "autofix":  false,
    "docs":     "patterns.html#anatomy"
  },

  "detectedBy": "module-graph"
}

Why each field is there

ruleIdStable across renames and refactors, so an agent can tell "my fix worked" from "a different rule now fires". Without it there is no loop, only guessing.
statementThe rule in the architecture's own words, carried with the failure. The agent gets the intent, not just the symptom.
confidenceTells the agent when to stop. A proxy failure means the check is an approximation — satisfy it, then leave it alone rather than contorting the code to please a heuristic.
evidenceThe actual edge or value that broke, not a line number. An agent can reason about from → to; it cannot reason about "line 4".
remedy.allowedThe constraint to solve within, machine-readable. This is the single most useful field: it converts "you are wrong" into "here is the space of right answers".
remedy.autofixHonest about the minority that are mechanical. Most architecture violations are refactors, and claiming otherwise invites an agent to apply a syntactic fix that satisfies the check and breaks the design.
The loop this enables. Run, receive typed diagnostics, fix the highest-authority ones first, re-run, compare rule ids. That loop closes without a human in it, and it is impossible against six unrelated output formats.

10 · The framework, as designed

Four components. None of them evaluates a rule — that is deliberate, and it is what keeps this small enough to finish in wave 0.

The trick that makes it work. The rule id is written into each tool's own config — as the graph rule's name, the lint rule's message id, the test's name. Every tool then reports it back in its native output for free, and the adapter is a lookup rather than a parser guessing at intent.

Built for scale

O(1) to add a ruleA new rule is a new entry of an existing contract type. No new code, no new config file, no new adapter. The moment adding a rule requires code, the registry has failed.
incremental by defaultOnly changed files and their dependents are re-checked locally; the full set runs in CI. The graph is cached against a hash of the manifest plus the file list.
layers run in parallelThe six layers share no state. Slowest wins rather than the sum, which matters once the gate suite grows past a few seconds.
coverage is computedAdding a rule with no check raises the judgement count and lowers the automated percentage automatically. The number cannot be claimed, only measured.
one schema, many producersA new tool becomes a new adapter, not a new output format for everyone downstream to learn. The agent contract never changes.

The classes

Nine types, three of them interfaces. Everything else is data passing through.

How it runs

// package.json — two scripts, that is the whole wiring
{
  "scripts": {
    "arch":      "archcheck",          // joins the existing check suite
    "arch:emit": "archcheck emit"            // regenerates configs + docs
  }
}

// the four moments it is invoked
editor      ← emitted configs, no invocation at all
pre-commit  ← archcheck --changed          // seconds, changed files only
CI          ← archcheck --all --format sarif
agent hook  ← programmatic, below
// programmatic — what an agent hook calls
import { ArchCheck } from 'archcheck';

const arch = await ArchCheck.load();
const { diagnostics, ok } = await arch.check({ files: changedFiles });

if (!ok) {
  // typed, ranked, with a remedy each — hand straight back to the model
  return { block: true, feedback: diagnostics.filter(d => d.confidence === 'deterministic') };
}
One binary, four entry points, no daemon. A check run is a graph walk over changed files plus their dependents; the full pass is CI's problem. Nothing is resident, nothing watches the filesystem.
What we deliberately do not build. No rule engine, no query language, no code model, no graph database. Those exist, they are better than ours would be, and none of them is the missing piece. If this ends up looking like a thin registry plus an adapter layer, that is the design succeeding rather than being unambitious.

11 · Integrating it

Two files change. Adoption has to be cheap or it does not happen — and a rule engine nobody installs enforces nothing.

Who owns what

The boundary that makes this adoptable: a consumer writes rules and nothing else. If adopting it ever requires writing anything other than rules, the boundary has leaked.

you ownOne file of rules. Reviewable on its own, and an architecture change is a diff to it rather than edits scattered across a linter config, three scripts and a paragraph of prose.
you never touchThe generated configs. They carry a header saying so, and a hook enforces it — otherwise the first person to hand-patch one silently breaks the link back to the rule.
you never forkThe engine. Extending it means implementing one of the three seams in your own repo and registering it — never editing the package.
1 · installbun add -d archcheck
2 · initarchcheck init reads the folder structure and writes a starting architecture.config.ts — layers inferred from what is already there, every rule at warn. Nothing fails on day one.
3 · emitarchcheck emit writes the checker configs and the rule documentation. Commit them; they are generated output.
4 · wireOne line in package.json, one step in CI. That is the entire integration.
5 · promoteMove rules from warn to error one at a time as the code catches up. A rule that cannot be promoted yet is visible rather than absent. Every warn carries an owner and a date. A warn with neither is a rule nobody intends to enforce, and the engine is decorative from then on.
// architecture.config.ts — the whole integration surface
import { defineArchitecture } from 'archcheck';

export default defineArchitecture({
  root: 'packages/engine/src',

  layers: [
    { name: 'contracts',  match: 'packages/contracts/**',     mayImport: [] },
    { name: 'rules',      match: 'modules/*/rules/**',        mayImport: ['contracts'] },
    { name: 'domain',     match: 'modules/*/domain/**',       mayImport: ['contracts', 'rules'] },
    { name: 'service',    match: 'modules/*/services/**',     mayImport: ['contracts', 'rules', 'domain'] },
    { name: 'repository', match: 'modules/*/repositories/**', mayImport: ['contracts'] },
  ],                                    // undeclared = denied

  modules: { match: 'modules/*', publicSurface: 'index.ts' },

  rules: [
    { id: 'no-deep-module-imports', kind: 'encapsulation', severity: 'error' },
    { id: 'endpoint-declares-permission', kind: 'declared-field',
      on: 'routes/**', field: 'permission', severity: 'error',
      remedy: 'add requirePermission(...) to the route registration' },
  ],
});
Why init matters more than it looks. Handing someone a blank config and ninety-one rules to write guarantees they will not. Inferring the layers that already exist, setting everything to warn, and letting them promote rules one at a time turns adoption into a gradient instead of a cliff.
But not in wave 0. Inference has nothing to read on a greenfield repo — there is no structure yet to infer. Write the first config by hand, and build init when there is a second repository to adopt into. It is the nicest feature here and the least urgent.

12 · Extending it

Three seams, and a new requirement lands on exactly one of them. This is the test of whether the design holds: if a future rule needs a fourth seam, the model was wrong.

New kind of rule → ContractType

Implement emit() so it becomes checker config, and explain() so a finding becomes a remedy. Example: "every public method is documented" is a new kind; "services may not import transport" is not — it is an instance of layers.

New checker → Probe

Implement run() returning raw findings tagged with a rule id. A security scanner, a schema differ, a bundle-size budget. The rest of the pipeline is unchanged.

New audience → Reporter

Implement report(). A dashboard, a chat notification, a different CI annotation format. The diagnostic schema does not move.

most rules add nothingA new instance of an existing contract type is one entry in the config. No code, no build step, no adapter. This is the common case and it has to stay the common case.
the schema is the contractAnything that consumes diagnostics — an agent, CI, a dashboard — is insulated from every change upstream. Add ten probes and no consumer changes.
versioned, because agents read itThe diagnostic shape carries a version. A model may have been trained or prompted against an older shape, so a breaking change to that schema is a breaking change to the product.

13 · Is this foolproof?

No. And no version of it can be. Of the ninety-one rules, sixty-five are decided by a script, eleven are approximated, and fifteen have no check at all. What follows is exactly where the holes are, and which ones are worth closing — because the answer is not "write more checks".
✓65decided
◑11approximated
○15no check
71%machine-decided · the other 29% needs a reader

Five things escape it

intentFifteen rules. "Names are honest", "the comment explains the rule", "no business logic in middleware". A machine cannot read intent, and a check that pretends to will either pass everything or block correct work.
approximationEleven rules where the check is narrower than the rule. "Controllers stay thin" is a complexity cap; the real rule is about what kind of decision lives there. A green result is evidence, not proof.
runtimeEverything here is static. It says nothing about whether the transaction actually commits atomically, whether a retry is idempotent under load, or whether the code is correct. Architecture conformance is not correctness.
the rules nobody wroteThe largest practical gap. Default-deny covers it structurally — an undeclared folder fails — but only for the structural kinds. A semantic rule nobody thought of is simply absent.
the architecture being wrongEvery check proves the code matches the declared architecture. None proves the declaration is the one you wanted. This gap does not close, at any level of investment.

The answer is not more checks

Enforcement has strength levels, and almost every rule we have sits in the middle one. Moving a load-bearing rule up this ladder is worth more than adding ten new rules at the level it is already on.

1 · impossibleThe invalid state cannot be represented. A type that will not compile, a dependency that is not installed, a database grant that does not exist. Nothing to enforce, because nothing to violate.
2 · blockedRejected before it lands — a pre-write hook, a pre-commit gate. The violation never enters the repository.
3 · detectedFound after it lands, in lint or CI. Where fifty-eight of our rules currently live. Reliable, but it caught something that already happened.
4 · reviewedA reader or a model judges. Fifteen rules, and the weakest link that still counts as enforcement.
5 · documentedWritten down and nothing else. Where every rule starts, and where a rule quietly returns when its check is deleted or never matched anything.

Nine rules worth promoting to impossible

Each of these is currently detected. Each can be made impossible with no new checking machinery at all — which is the only kind of foolproof there is.

Implementations bound only in the composition rootgraph rule implementations are not exported from the package; only the root resolves the internal path

This is where the effort belongs. Nine rules move from "we will notice" to "it cannot happen", and they are the nine that would hurt most if violated. None of them needs the engine — they are type signatures, package manifests, database grants and container policy. The engine handles the eighty-two rules that cannot be made impossible.

What remains, stated plainly

Fifteen rules rest on a reader

Now written in English and checked by a model in the same run — see §14. Better than nothing, weaker than a check, and labelled as such on every line.

Eleven are approximations

Recorded as such, so nobody mistakes a green build for a proof. The alternative — marking them decided — is how a check suite starts lying.

Correctness is a separate problem

Conformance and correctness are different questions. This answers the first one only; tests answer the second.

The declaration can be wrong

Which is why the manifest is reviewed like a design document and changed in its own commit, never as a line buried in a feature.

So: foolproof for what, exactly. For structural drift — the layer that gets imported the wrong way, the barrel that gets bypassed, the endpoint that ships with no permission — yes, and increasingly so as rules move up the ladder. For whether the code does the right thing, no, and that was never this tool's question.

14 · The other fifteen — rules a model verifies

One registry, two kinds of verification. Rules a script can decide are checked by a script. Rules it cannot are written in plain English and checked by a model. Both live in the same file, run from the same command, and report in the same schema — labelled so nobody confuses one for the other.

This needs no change to the architecture. A model verifier is a Probe like any other: it takes a file set, returns findings tagged with a rule id, and the normaliser attaches the statement and remedy. The seam was already there.

A rule in plain English

{
  id:        'honest-function-names',
  kind:      'judgement',                  // the new contract type
  severity:  'advisory',                   // advisory | blocking | off

  statement:
    'A function name must describe what the function actually does. ' +
    'If it conditionally skips its stated work, it is misnamed.',

  appliesTo: 'modules/**/*.ts',            // scope — never the whole repo
  cite:      'the function declaration',   // what evidence to return

  examples: {                             // the single biggest quality lever
    pass: 'loadPageIfStale() — skips when fresh, and says so',
    fail: 'loadInitialPage() — returns early when cached',
  },
}
Prose, but not freeform. Anyone can add a rule without writing code. The four structured fields around the sentence are what make it checkable rather than a wish: scope keeps it cheap, examples calibrate it, and cite forces the model to point at something a person can verify.

Execution order

archcheck
  │
  ├─ 1 · deterministic     65 rules · every layer · milliseconds to seconds
  │        └─ any failure here STOPS the run
  │           no point paying a model to judge structurally broken code
  │
  ├─ 2 · proxy             11 rules · reported with their approximation flag
  │
  └─ 3 · judgement         15 rules · model · diff-scoped · advisory by default
           └─ cached by (ruleId, content hash) — unchanged code is not re-judged
Deterministic first is not just ordering, it is a cost control. A failing layer rule means the model call was never made. In the common case where structure is fine, only the changed files reach step 3.

Five things that decide whether this works

advisory by defaultA model verdict never blocks the build until that specific rule has earned it. A flaky gate gets disabled, and a disabled gate enforces nothing. Promotion to blocking is per-rule and deliberate.
scoped and cachedEach rule declares what it applies to; runs are diff-scoped; verdicts cache against a content hash. Without all three this is too slow and too expensive to keep switched on, and the first thing anyone does is switch it off.
examples, not just a sentenceOne passing and one failing case per rule. This is what separates a verifier that finds real violations from one that flags everything and trains people to ignore it.
evidence requiredThe model must cite the exact span it judged. A verdict with no citation is discarded, which removes most confident-sounding noise automatically.
code is data, never instructionThe files under review are quoted input. A comment in a source file saying to ignore the rule is a string, not a command.

The same schema, one honest field

{
  "ruleId":     "honest-function-names",
  "statement":  "a function name must describe what it actually does",
  "confidence": "model",          // deterministic | proxy | model
  "severity":   "advisory",
  "location":   { "file": "modules/ledger/services/write.ts", "line": 42 },
  "evidence":   { "cited": "export async function loadInitialPage()" },
  "remedy":     { "summary": "rename to reflect the early return, or remove it",
                  "autofix": false },
  "detectedBy": "judgement-probe"
}

An agent consuming this sees one stream and knows exactly how much to trust each item. confidence: "model" means consider this, verify it yourself — not obey it. A deterministic failure is a fact; a model verdict is a second opinion.

What this does and does not promise

Does · one place

All ninety-one rules in one file, one command, one output. Nobody has to remember that fifteen of them live somewhere else or get checked by a different process.

Does · anyone can add one

A rule in English with two examples. No code, no contract type, no adapter — the lowest barrier to capturing a convention the moment someone notices it.

Does not · guarantee

A model may miss a violation or invent one. The run says so on every line. These rules are not, and will never be, the same thing as the sixty-five.

Does not · replace promotion

If a judgement rule turns out to be mechanically checkable, it moves. The English version is where a rule lives until someone finds a way to decide it.

The failure mode to watch. Plain-English rules are so easy to add that the set grows faster than anyone calibrates it, and precision quietly falls until the whole advisory stream is skipped. Track per-rule hit rate; a judgement rule that has produced nothing actionable in a month is noise and should be deleted or rewritten, not left running.
